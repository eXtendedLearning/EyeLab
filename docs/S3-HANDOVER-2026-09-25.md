# S3 / S3b handover — 2026-09-25

State of the XREAL native head-pose work at the end of the 2026-09-23..25
sessions, written so the next session can continue without re-deriving anything.
Full evidence: `NEBULA-WINDOWS-AUDIT-2026-09-21.md` §§11–14. Plan of record:
`adr/0003-eye-pov-rigid-coupling.draft.md`.

## Where S3 stands in one paragraph

Raw IMU (S3 as originally planned) is **licence-blocked**: every `NRImu*` export
sits behind an NRSDK licensed-feature gate, the licensed-feature list on this
machine is empty, and the call returns 22 `LicenseFeatureUnsupported`. S3b was
opened as the way round it — the *fused* head pose, which is not gated. Its call
chain is now complete and provably correct, but **it delivers no data**: 1930
poses in 20 s, every one the exact 4x4 identity, stamped 0, with tracking reason
1 `Initializing`. The tracker never starts. Three candidate causes remain; the
cheapest one has been refuted.

## What is confirmed, and will not need doing again

* **Signatures.** The whole `NRPerception*`, `NRHeadTracking*`, `NRHeadPose*`
  chain, recovered from `XREALXRPlugin.dll`'s own call sites and the export
  thunks. Audit §§11–12 have the tables. All of it verified by clean runs.
* **The bring-up order.** `NRAPICreate` → `InitSetNetworkType(0)` → `NRAPIStart`
  → `NRPerceptionGroupCreate` → `GetCount` → per index `GetPerceptionId` +
  `GetSupportedFeatures` → `NRPerceptionCreate(id)` → `NRPerceptionStart` →
  `NRHeadTrackingCreate(perception, &tracking)` → acquire/read/destroy →
  teardown in reverse. Implemented in `python/xreal_perception.py`.
* **The licence gate.** Which families are gated and which are not: audit §11's
  table. `NRPerception*`/`NRConfig*`/`NRHeadTracking*`/`NRHeadPose*`/`NRHMD*`
  extrinsics are all ungated; `NRImu*`, `NRGrayscaleCamera*`, `NRVsync*`,
  `NRGlasses*` are gated. XREAL's FAQ confirms raw camera + IMU need the
  Enterprise version.
* **Error and reason names.** `XREALErrorCode` 0–24 and `NotTrackingReason` 0–8,
  decoded from Nebula's IL2CPP metadata into `python/xreal_result_codes.py`.
* **The pose payload is 64 bytes / 16 float32.** Its convention is still
  undetermined *because every sample so far has been the identity*, which fits
  every candidate layout. `python/headpose_analysis.py` will decide it as soon as
  a non-identity pose exists.

### Candidate causes, updated

1. ~~**The timestamp.**~~ **Refuted by pose 3.** `NRPerceptionGetHMDTimeNanos`
   returns a real, advancing device clock; passing it (plus offset) changes
   nothing. The returned pose is still stamped 0.
2. **The perception.** Strongest remaining lead. The group's enumeration is
   almost certainly not what it looks like: `GetCount` says 20 and
   `GetPerceptionId(i)` returns exactly `i+1` with a zero feature mask, and only
   **id 1** can actually be created. The SDK log names it:
   `Plugin Initialize failed: retcode=1, id=nr_perception_id_remote` — so
   perception ids map to named plugins and id 1 is the *remote* one, which is
   very unlikely to be the head-tracking perception. Finding the real id/name
   map is the next job. `nr_perception_id_*` is not a plain string in any vendor
   DLL (built at runtime or obfuscated); `nr_imu_tracking` and
   `nr_imu_calibration` *are* present in `libnr_api.dll` and look like sibling
   plugin names.
3. **A missing start step.** `libnr_plugin_6dof.dll` (loopback
   `127.0.0.1:53004`, audit §9) is shipped and never started by us. The
   perception layer is plugin-backed, so this is plausible.
4. **The licence.** 6DoF SLAM needs the grayscale cameras and 3DoF needs the
   IMU; both are refused with 22. A tracker with no sensor can legitimately sit
   in `Initializing` forever. `nr_imu_tracking` existing as a plugin name is
   weak support. If 2 and 3 come back negative this is the answer, and Enterprise
   access becomes a hard dependency for S3b as well as S3.

## Two uncontrolled variables — read before trusting the sweep

* **Nebula was run and it updated the glasses' firmware** at the end of the
  session, after these runs. Device state and firmware version have changed
  since every measurement above. Re-run S0 (`python/xreal_probe.py`) first to
  record the new firmware, and treat the runs above as pre-update.
* **The sweep may be invalid.** Its `NRPerceptionStart` failed with
  `get device config failed` / `PerceptionBase Init failed` /
  `LeopardClient remove connection(0) ... disconnect`, while the pose run 35 s
  later started the same perception id successfully. Nebula being up, or the
  update in progress, would explain a transient device-config failure. **Re-run
  the sweep on a clean machine state before drawing any conclusion from it.**

## One probe fix made after the runs

`HeadPoseReport.ok` used to mean "samples were recorded", so runs 2 and 3 printed
`verdict OK` over recordings in which every pose was the identity. It now requires
at least one non-identity pose (`delivered_data`), counts `identity_samples`, and
sets an explicit error — *"all N poses were the identity transform: the calls
succeed but the tracker is not producing"*. Re-running the same conditions will
now report `incomplete`, which is the truthful answer. 43 tests.
