## Step 0 — versions and firmware (Jack; before the glasses touch the Beam Pro)

Decided 2026-11-16: accept the current updates once, record everything, then freeze until the end of the
publication campaign. Reason: SDK, MyGlasses runtime and glasses firmware are a matched set (release notes of
SDK 2.3.x and 3.1.0 tie SDK builds to MyGlasses and firmware versions; 3.1.0's 6DoF with Eye needs current
firmware). A change of firmware can change the Eye stream (exposure, crop, timestamps) and invalidate
calibrations and latency numbers, so it must be a recorded event, not a background one.

1. Record the glasses firmware **now**, on the desktop, before any Beam Pro contact
   (`python python/xreal_probe.py`, S0, or the xreal.com/ota page). It is also the pending S0 re-run.
2. Start the Beam Pro **without the glasses**. Connect Wi-Fi, apply the Beam Pro OS update and the MyGlasses /
   XREAL Store updates.
3. Connect the glasses; let MyGlasses update their firmware (community reports say it starts within
   10-20 min on Wi-Fi). Note the version shown in MyGlasses.
4. Freeze: MyGlasses developer page (tap the glasses icon 10 times with no glasses connected, per the XREAL
   FAQ). Community reports describe an OTA switch there; it is **not** in the official docs, so verify it.
   If there is none, keep the Beam Pro off Wi-Fi during the campaign period except when needed.
5. On the Surface, re-run S1 (glasses as display) to learn whether the PC-beta backup still works on the new
   firmware. Record the answer in `docs/HARDWARE.md`.
6. Write every version into `docs/HARDWARE.md` and `docs/CAPABILITIES.md`: Beam Pro build, MyGlasses,
   glasses firmware, XREAL SDK in the APK (3.1.0), Unity (6000.4.5f1). `beampro.bat` → 2 dumps the package
   versions; the firmware is read by hand from MyGlasses.

## B0 — the APK runs on the Beam Pro with the glasses as display

Prerequisite: Unity 6000.4.5f1 + Android Build Support with OpenJDK and Android SDK & NDK Tools (brings
`adb`, which `beampro.bat` finds). Installed on `lagann-0526` 2026-11-17; the first probe APK built there in
batch mode with 0 errors (compile check of the probes and `BeamProInventory.java` passed).

Steps:

1. Jack: on the Beam Pro, Settings → About → tap build number 7× → Developer options → USB debugging on.
   Connect it to the desktop; accept the RSA prompt. (Device settings are Jack's, AGENTS.md "Unity".)
2. Build the APK. Either the agent, in batch mode (AGENTS.md "Unity" allows it):
   `Unity.exe -batchmode -nographics -quit -projectPath eyelab_xreal -buildTarget Android -executeMethod
   EyeLab.Probes.Editor.ProbeSceneBuilder.BuildApkBatch -logFile eyelab_xreal/build/probes_build.log`
   (creates the Probes scene and writes `eyelab_xreal/build/eyelab_probes.apk`), or by hand: Unity 6000.4.5f1,
   open `eyelab_xreal/`, menu **EyeLab → Probes → Create Probes Scene**, Build Profiles → Android → Build to
   `eyelab_xreal/build/eyelab_probes.apk`. Compile errors in `Assets/EyeLab/Probes/` or
   `BeamProInventory.java` stop the gate: the probes were reviewed against the 3.1.0 SDK sources but not yet
   compiled.
3. `beampro.bat` → 1 (device listed), → 3 (install).
4. MyGlasses developer page → "select other MR App" → EyeLab XREAL. Put the glasses on and start it **once
   with no `probe.json`**. The Beam Pro screen first shows XREAL's controller; tap **App** in the middle to
   reach EyeLab's buttons; press "Inventory + IMU 20 s" with the Beam Pro still on the table, then
   **Quit EyeLab**. The first start also creates the app's files folder; pushing `probe.json`
   (`beampro.bat` → 4) before that would create the folder as the adb shell user, which the app may then not
   be able to read. Use → 4 only from the second start on.

Findings of the first install (2026-11-17):

- The first APK aborted at XR start (`NameResolutionException com/xreal/framework/net/binder/Connection`):
  the old SDK patch script had dropped `libs/framework.jar` from `nr_common.aar`. Fixed in the script; re-run
  `tools/patch_xreal_sdk.ps1` on any clone patched before 0.4.000.
- The Beam Pro cannot have the desktop cable and the glasses connected at once. Install over adb, unplug,
  connect the glasses, start from MyGlasses, run; then reconnect and pull the runs and
  `cache/auto_log`. Started over adb without the glasses the app stays up, but the XREAL loader times out
  waiting for the runtime service and the session is not created (expected, not a defect).
- With the glasses connected the XREAL session came up (display, tracking, IMU, grayscale cameras), but no
  buttons appeared: the player loaded SampleScene. A `data.unity3d` left in Unity's Gradle project by a May 2026
  build was packed into the APK next to the fresh scene files and won. `BuildApkBatch` now removes it before
  every build and fails when an APK holds both (CONTEXT.md, "Android settings"). Two permission dialogs
  (Unity's storage request, CAMERA at start-up) also opened on the Beam Pro screen unseen; both are gone.
- With the right scene the buttons showed (after tapping **App** on the XREAL controller screen, which switches
  the Beam Pro screen to the app's own canvas) but did not react: neither the SDK's virtual controller prefab
  nor the Probes scene has an EventSystem (the SDK samples get one from the XR Interaction Setup prefab). The
  runner now creates one with `InputSystemUIInputModule` (the project uses the Input System only).
  Any future EyeLab scene with phone-screen UI needs the same.
- The app cannot be closed from the glasses: the Beam Pro screen has a **Quit EyeLab** button; the agent can
  also `am force-stop` it. With the Beam Pro screen asleep the activity is paused and nothing runs.
- `MainThreadWatchdog.cs` (diagnostic, tag `[EyeLab watchdog]`) logs the loaded scene with its roots, and the
  main thread's frame rate every 5 s. Kept for B0/B1; remove when the bring-up is closed.
- Unity's "referenced script is missing" warnings on the `XREALVirtualController` object are the SDK's
  Editor-only hand simulator, compiled only with the XR Hands package: harmless.

**Result (2026-11-17):** passed except the last clause. The app runs with the glasses (XREAL
session, display 18, head tracking start), main thread 43-47 fps; the Beam Pro screen shows the status line,
the three probe buttons and Quit, and they react; run `20261117_220142_inventory` pulled and analysed.
Nothing is drawn in the glasses: the Probes scene has no content in front of the user, so the glasses show
only the transparent background. That is expected for these probes; seeing EyeLab content in the glasses is
the next step (B1's timecode and the overlay). Open: the glasses firmware version (`HARDWARE.md` has the
Beam Pro build, RAM/storage and the MyGlasses package version; the firmware is not yet read). The APK of these
runs was stamped 0.3.012, the uncommitted build that was released as 0.4.000.

**Done when:** the app runs with the glasses as display; the Beam Pro screen shows the status line and
the three probe buttons and Quit (or runs the chosen probe); `beampro.bat` → 5 pulls a `BeamProRuns/<stamp>_inventory`
folder; the versions of step 0 are in `HARDWARE.md`.

If the buttons do not appear: the virtual controller canvas was not found and the fallback overlay canvas
did not reach the phone screen. Report it; the timecode in T6.1 uses the same canvas.

## BS — what the Beam Pro's own sensors give

### Questions

1. **Rear cameras.** How many camera ids does a third-party app see? Is there a logical rear camera with two
   physical members? Are the two physical cameras listed in a concurrent-camera set, or reachable as
   physical streams of the logical one? Sensor sync type (`calibrated` = hardware-synchronised exposures,
   `approximate` = not)? Intrinsics (`LENS_INTRINSIC_CALIBRATION`), lens pose
   (`LENS_POSE_TRANSLATION/ROTATION`, reference) and timestamp source (`realtime` = BOOTTIME)?
2. **IMU.** Which accelerometer and gyroscope, at what rate, with how much delivery lag, and are the event
   timestamps on BOOTTIME (they are compared with `SystemClock.elapsedRealtimeNanos` at delivery)?
3. **Displays.** Is the glasses display an Android display, with which modes and presentation deadline?

### Protocol

- `beampro.bat` → 2: adb dumps (`dumpsys media.camera`, `sensorservice`, `display`, `usb`, getprop, packages).
  These show what the system knows, including cameras an app may not see.
- Start the app and press "Inventory + IMU 20 s" (or, from the second start on, `beampro.bat` → 4 → a and
  start the app); keep the Beam Pro **still on a table** for the 20 s IMU recording, → 5 pull, → 6 analyse.
  This shows what the app sees.
- Compare the two. Where they differ (e.g. a physical camera in dumpsys but not in the app's list) the app's
  view is the one that counts.

**Done when:** `python -m xreal_gates bp <inventory run>` prints the camera table, the IMU rates and lag,
and the displays; the answers to questions 1-3 are written into `docs/CAPABILITIES.md` (new rows) and
`docs/HARDWARE.md`.

### Results (2026-11-17, run `20261117_220142_inventory`, the app's view)

1. **Rear cameras:** Camera2 lists ids `0` (back) and `1` (front) only. Neither is a logical multi-camera
   (capability 11 absent, no physical ids, no sync type), and the concurrent sets are `[1]` and `[0, 1]`.
   **A third-party app cannot open the second rear camera, so there is no Beam Pro stereo.** Rear `0`: array
   4088x3080, 2.16 mm, f/2.2, factory intrinsics fx 1684 / fy 1683 px at full array, principal point (2040,
   1536), about 101° horizontal field of view; distortion coefficients not given (all zero); lens offset
   (-9.5, -0.1, 0) mm from reference 0; timestamp source `realtime` (BOOTTIME); AE up to 30 fps.
2. **IMU:** ICM-4x6xx accelerometer and gyroscope (and their uncalibrated twins), 401.4 Hz with even periods,
   BOOTTIME stamps, delivered 2.1 ms after the event (median, p95 3.1 ms).
3. **Displays:** the glasses are Android display 18 "HDMI Screen", 3840x1080 @ 60 Hz in use, 1920x1080 @ 90 Hz
   also offered; presentation deadline 16.7 ms.
4. **Clocks (not asked, found):** the XREAL HMD clock in the app equals CLOCK_MONOTONIC (bracketed by two
   MONOTONIC reads at start and at end). BOOTTIME − MONOTONIC = 5969.045 s, constant to 2 µs. Beam Pro camera
   and IMU stamps (BOOTTIME) map onto the HMD clock by that one offset while the device stays awake.

Still to do for the gate: `beampro.bat` → 2 (adb dumps) and compare with the above; then the BS rows in
`CAPABILITIES.md` (rows 22-24) can lose their "app's view only" note.

### What BS decides (and what it cannot)

The Beam Pro's two 50 MP rear cameras are 50 mm apart. They are **not** rigidly attached to the glasses, so by
ADR-003 they cannot give the overlay pose. They can still serve as:

- **an independent fixed observer** on a tripod during validation (an external pose of the plate and,
  if a marker is put on the glasses, of the head), compared with the Eye's chain;
- **a stereo survey** of a structure's marker layout before a test;
- **an IMU / inclinometer** for the setup assistant (as `python/surface_imu.py` does on the Surface).

**Update 2026-11-17: the stereo survey above is out: an app sees only one rear camera.** The single rear
camera still serves as a fixed observer, for a monocular PnP survey, and its IMU as an inclinometer.
Precision, for orientation only (written before the inventory): with an assumed f ≈ 960 px at 1080p, a 0.3 px
disparity error gives σZ ≈ Z²·σd/(f·B) ≈ 2.3 mm at 0.6 m (the measured rear camera, ~101° wide, has about
f ≈ 790 px at 1920 px width, so worse), worse than single-camera PnP on known markers (0.27 mm median
at 0.6 m in a noise-only synthetic sweep of plate A, 2026-10-08). Stereo's real gain is removing the planar mirror ambiguity
suspected in the B1 webcam campaign (900 mm frontal rotation jitter, October 2026), not depth precision.

**BS-2 (only if question 1 says yes):** dropped 2026-11-17, question 1 says no.
