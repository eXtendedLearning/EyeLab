## The latency budget, stage by stage

```
exposure ─► cam_ts ─► arrival in the app ─► detection + PnP ─► lock filter ─► render submit ─► glasses photons
   [B1: clock domain]  [B1: chain probe]      [B3a, needs ADR-0004]           [B5]              [B6, external]
```

On the Surface (guide §25-26): exposure → overlay 330 ms at the 0.3 s restart threshold, of which about 105 ms
was the CPU decoder queue and 55 ms plate detection; 680-700 ms at the 1.0 s threshold. The Beam Pro question
is whether the Android SDK path has that queue at all (`libmedia_codec.so`, possibly hardware decoding).

Why it matters for the overlay: the warp of the XREAL runtime compensates the head pose at display time, not
the age of our marker pose. Each frame is paired with the head pose at its own capture time (proven on the
Surface, §24-26), so the residual depends on how exact the frame age is and how much the head moves within it.

## Probes (in the APK of T6.0)

- **chain** (5 min): `EyeChainProbe.cs` acquires every Eye frame with the same draining loop as the PC gates
  (acquire until nothing newer is queued, keep the newest, count the drained ones) and logs `cam_ts` next to
  CLOCK_MONOTONIC, CLOCK_BOOTTIME, CLOCK_REALTIME (libc `clock_gettime`), the HMD clock and Unity time, read at
  arrival (`eye_frames.csv`). One full-resolution Y plane every 10 s goes to `snapshots/` for orientation and
  the B4 calibration check. No detection runs.
- **timecode** (60 s): the same chain, plus `TimecodeScreen.cs` drawing a DICT_6X6_1000 marker whose id is a
  counter mod 1000 on the **Beam Pro's own screen** (the virtual controller canvas), redrawn every Unity frame
  and logged on the same clocks (`draws.csv`). Every Eye frame is saved half-size to `frames/` and decoded
  offline. Since draw and arrival are read on the same device and the same clock, no synchronisation is needed.

What the timecode measures is an **upper bound** on exposure → arrival. The excess is the Beam Pro panel's
presentation delay plus the wait for the next exposure (0 to 1 frame period, mean half). The second line,
draw → `cam_ts`, tells what `cam_ts` stamps: if it is exposure time on the arrival clock, it is ≥ 0 and
about panel delay + half a frame.

Arrival is read in Update, so it is quantised to one Unity frame. That bias is in the number and is stated.

### Analysis

`python -m xreal_gates bp RUN` (`python/xreal_gates/beampro.py`):

- tries every clock × unit (ns, µs, ms) for `cam_ts` and keeps the one with a positive, stable age
  (0-5 s, smallest IQR); prints the others that are also plausible. If the Beam Pro has not slept since boot,
  BOOTTIME and MONOTONIC coincide and both will be plausible: that is expected, not a failure.
  *Found in the T6.0 inventory run (2026-11-17):* this Beam Pro had already slept, BOOTTIME − MONOTONIC was
  5969 s, so the two separate cleanly; `GetHMDTimeNanos` works on Android and reads CLOCK_MONOTONIC. A `cam_ts`
  on the HMD clock will therefore show up as MONOTONIC.
- age drift in ms/min (a growing age means a queue), frames drained, kept fps;
- timecode: decoded frames, row order (as delivered or flipped), draw → arrival median / p10 / p90, draw → `cam_ts`.

## Results (2026-11-17, build 0.4.001, glasses SW `15.1.03.603_1.9.1.20260914175625_097`)

Runs `20261117_225102_chain` (5 min worn, looking around) and `20261117_225617_timecode` (60 s); main thread
42 fps throughout (watchdog).

1. **Stream:** 1280x720 Y plane (stride 1280), camera period 33.53 ms (29.8 Hz), 29.2 fps kept. About 2 % of
   frames never reach the app (188 of 8916 in 5 min, longest gap 134 ms): the API hands out only the latest
   image, and the 42 fps loop sometimes misses one. Rows arrive **upright** (snapshots: shelves, frame and coat
   stand the right way up), unlike the bottom-up Windows buffer.
2. **Clock:** `cam_ts` is in ns on the HMD clock, which is CLOCK_MONOTONIC on the Beam Pro (`hmd_ns` and
   `mono_ns` give the same age; BOOTTIME differs by 5969 s and is ruled out). `GetHMDTimeNanos` is non-zero in
   every row. The Windows result (`cam_ts` on the HMD clock) carries over, so `HMD now − cam_ts` is the exact
   frame age here too.
3. **Queue:** none. Age at arrival median 152 ms (p5 127, p95 193, max 269), per fifth of the run 156, 155,
   154, 149, 148 ms: flat, no growth (drift −3 ms/min). 0 drained frames. The Surface had a 0-450 ms decode
   sawtooth on top of a 70-80 ms base; the Beam Pro has no sawtooth but a base about 70 ms higher. The age
   includes up to one Update period (24 ms at 42 fps) of read-out quantisation.
4. **Timecode: 0 of 1725 frames decoded.** The marker was in view (snapshots) but unreadable: the Eye was
   about 60-70 cm away instead of 30-40, so the marker was about 70 px wide; the screen at full brightness in
   a dim room saturated it (black cells read 200+ of 255); and the probe redrew a new id every 20 ms while the
   Eye, auto-exposing for the dark room, integrates up to a whole 33 ms frame, so most exposures held two
   ids. The last one is a design error of the probe, not of the protocol. Fix in T6.2: hold each id for
   ≥ 100 ms (3 camera frames), grey-on-black drawing at lower brightness, and use only the first frame that
   shows a new id.

## Later: the photon end (B6)

The overlay's motion-to-photon cannot be read from inside the app. Two external methods, neither needed for B1:

- **Photodiode** (BPW34 or similar into an Arduino analog input, sampled ≥ 2 kHz): one diode on the Beam Pro
  screen where the app flashes a patch, one behind a glasses lens where the overlay flashes in response to an
  Eye event. Gives the panel delay that the timecode bound contains, and the full loop (Di Luca 2010,
  Presence 19(6)). Jack has the parts at home; not for tonight.
- **Slow-motion video** of screen and lens together. Galaxy M55: its Camera app has a Slow motion mode, but
  the capture rate was not found in a trusted spec sheet. Check it on the phone (Camera → More → Slow motion →
  settings) and confirm in the file (MediaInfo or `ffprobe`; Android stores the capture rate in the
  `com.android.capture.fps` tag, while the container may say 30 fps). 120 fps gives ±4.2 ms per sample,
  240 fps ±2.1 ms; averaging over ≥ 100 events reduces both.

## Regenerating `TimecodeBits.cs`

The marker table must match OpenCV's DICT_6X6_1000. It was generated with:

```python
import cv2
d = cv2.aruco.getPredefinedDictionary(cv2.aruco.DICT_6X6_1000)
img = cv2.aruco.generateImageMarker(d, marker_id, 8)   # 8x8 cells incl. border
bits = (img[1:7, 1:7] > 127).flatten()                  # row-major, 1 = white, first bit = MSB (bit 35)
```

Checks at generation: id 0 = `0x1E3DD82A6`, id 123 = `0xB0351F9EE`; every 7th id re-rendered from the table and
detected back with `cv2.aruco.ArucoDetector` (0 errors).
