**Date:** 2026-09-18 · **Commit audited:** `c3c01ff` (worktree clean) · **Auditor:** Claude (Opus 5)

## 1. Method

All claims below were reproduced in an isolated venv at CI parity (Python 3.11, `opencv-contrib-python` 4.14.0 — the highest version satisfying the `<5.0` pin — numpy 2.4.6, scipy 1.17.1, pyuff 2.5.6), built from `python/requirements.txt`. Sources were staged read-only; nothing in the repo was modified.

Baseline: the existing suite is **68 passed / 1 error**, the single error being the known `tkinter`-absent failure in `test_gui_calibration`. Overall statement coverage is **33 %**.

Every finding carries the probe that produced it. **Seven hypotheses I formed while reading the code did not survive measurement and were discarded** — they are listed in §5, because knowing what is sound is as useful as knowing what is not.

## 2. Findings, severity-ranked

### S1 — Three independent silent scale errors, none visible to any existing quality gate

This is the headline finding, and the three instances share one signature: **a pure scale error produces a near-zero reprojection residual**, so `PoseLock`'s RMS gate, `SpatialRegistration.rms_error_mm`, and the calibration's `rms < 1.0 px` check all report "good" while the pose is grossly wrong.

**S1a — Printed markers are 20 mm; the configured default is 12 mm.**

`generate_markers.MARKER_SIZE_MM = 12.0` is the single source; `README.md` states 12 mm twice, `CHANGELOG.md` once. The only marker artefact committed to the repo — and the subject of the most recent commit (`c3c01ff`, 2026-08-21) — is `output/pdf/aruco_markers_20mm_A4.pdf`.

```
physical marker  : 20 mm       configured size : 12 mm
true depth       : 500.0 mm    reported depth  : 300.0 mm   (-40.0 %)
rotation error   : 0.000 deg   reprojection RMS: 0.0000 px   <-- perfect
```

The GUI exposes `marker_size_var`, so this is recoverable by the operator — but only if they know. Nothing warns.

**S1b — The calibration↔runtime resolution contract is written but never enforced.**

`save_calibration()` writes `image_width` / `image_height` into the YAML. `load_calibration()` returns only `(camera_matrix, dist_coeffs)` and never reads them back. No code anywhere compares the calibration resolution against the live capture resolution. `cap.set(CAP_PROP_FRAME_WIDTH, …)` is a *request* — many webcams ignore it — and `collect_from_images()` takes `image_size` from whatever stills it is handed.

Calibrating at 1920×1080 and running at the `ThreadedCapture` default of 1280×720:

```
true depth       : 500.0 mm    recovered depth : 747.8 mm   (+49.6 %)
rotation error   : 5.52 deg    reprojection RMS: 0.712 px   <-- passes every gate
```

**S1c — UNV units are neither applied nor correctly read.**

Two compounding defects in `unv_to_json._parse_units`:

1. It reads `dataset.get("unit_code", 1)` and `dataset.get("factors", …)`. pyuff's dataset-164 keys are `units_code`, `length`, `force`, `temp`. Both lookups miss, so **every file silently reports SI / `lengthFactor = 1.0`**, including one that explicitly declares MM_N_S:

```
file declares : units_code = 2 (MM_N_S), length = 0.001
parser reports: unit code 1 (SI), lengthFactor = 1.0
```

2. Even when read, the factor is never applied. Node coordinates are emitted verbatim; `lengthFactor` appears twice in the module, both times as a dict value, never as a multiplier. `eyelab_gui.py:951` assigns `parser.parse()` straight to `self.geometry_data` and never touches `["units"]`.

A 200 × 100 mm plate exported from Testlab in millimetres — the common case, unit code 2 — is consumed downstream as **200 m × 100 m**.

This has gone unnoticed because every test geometry is synthetic and SI: `generate_test_unv.py` ("SI units"), `unv_writer.py` (`units_code: int = 1`), and `test_assets/SKILL.md`, which instructs "Units are metres … Dataset 164 uses SI code 1". The skill is silently compensating for the parser defect.

> Also unapplied: dataset 2420 coordinate systems. `_parse_coord_systems` extracts origin and axes and maps `cs_type` to `{0: rectangular, 1: cylindrical, 2: spherical}`, and nodes carry `exportCS` / `displacementCS` IDs — but no code transforms node coordinates into a common frame, and no cylindrical/spherical→Cartesian conversion exists. A multi-CS or cylindrical Testlab geometry parses without error and is wrong. `eyelab_gui.py:950` additionally passes `validate_cs=False`, disabling even the CS-existence check.

### S2 — `SpatialRegistration.compute()` rejects every coplanar marker set, including exact noise-free data

`compute()` gates on `_condition_number(P) > 1e6`, documented as a collinearity check. The metric is `λ_max/λ_min` of the centred point covariance — a **rank-3** (full-3D-spread) test, not a rank-2 (non-collinearity) test. Three points in 3-space span at most a plane, so `λ_min ≈ 0` by construction.

```
3 non-collinear coplanar markers  cond = 1.000e+10  -> REJECT
4 coplanar (square face)          cond = 1.000e+10  -> REJECT
4 non-coplanar (box corner)       cond = 5.828e+00  -> accept
3 collinear (true degeneracy)     cond = 2.000e+10  -> REJECT

end-to-end on exact, zero-noise data:
  3 coplanar        -> compute() = None
  4 coplanar square -> compute() = None
  4 non-coplanar    -> ok, rms = 1.65e-13 mm
```

Markers on a flat plate — the most ordinary EMA specimen there is — can never register. This contradicts the project's own theory reference, `.docs/THEORY.md` §7.2: *"**Minimum points: 3 non-collinear correspondences.**"* The theory is right; the code is wrong.

The correct gate is a rank-2 condition: reject when `λ₂/λ_max` is below a relative threshold (collinear), not when `λ_min/λ_max` is.

This is currently masked in board mode, which is why it has not surfaced — see S5.

### S3 — The pose-lock gates are bypassed precisely where the dangerous failure lives

`PoseLock._accept()` opens with `if n >= cfg.acquire_min_markers: return True` — unconditional acceptance at ≥3 markers, in **every** state including LOCKED. The RMS and translation/rotation jump gates only ever inspect low-marker-count poses.

```
after 10 good 3-marker frames: state = locked
feed a 3-marker pose: 30 cm jump, 40 deg rotation, 25 px reprojection RMS
  accepted? True     reject_reason = None      state = locked
the IDENTICAL bad pose carrying 1 marker instead of 3
  accepted? False    reject_reason = rms
```

The inversion matters because the planar mirror ambiguity — the failure this layer exists to survive — **requires ≥3 coplanar markers to occur at all**. The one class of pose the gates never look at is the one class of pose most likely to be catastrophically wrong.

The inline comment justifies the bypass for *acquisition* ("gating acquisition on [baseline RMS] would prevent the lock from ever engaging"), which is sound. The defect is that the bypass is not restricted to the SEARCHING state.

### S4 — `.docs/THEORY.md` §6.3 gives a quaternion conversion that does not match its own matrix rule

The section states the OpenCV→Unity map as `t → (tx, −ty, tz)`, `R → F R F⁻¹` with `F = diag(1,−1,1)`, then says: *"if the rotation is in quaternion form (w, x, y, z), flip the signs of y and z."*

```
'flip signs of y and z' -> (w, x, -y, -z):  matches F*R*F^-1 in   0/500 cases
                           (w, -x, y, -z):  matches F*R*F^-1 in 500/500 cases
```

The stated quaternion rule is wrong. The section then instructs: *"Wrap this in one `CoordinateConverter` utility class and call it nowhere else — the moment this conversion gets duplicated, drift bugs follow."* Whichever of the two contradictory rules an implementer copies becomes the project-wide convention.

No `CoordinateConverter` exists yet, so this is latent — it lands the moment the Unity port starts. Given that `UDPPoseSender` already emits a raw quaternion with no handedness conversion and no frame declaration, and the CONTEXT.md WebSocket v0 protocol sends raw `rvec`/`tvec`, the conversion is entirely deferred to Unity-side code that has not been written.

### S5 — The registration is computed twice, by two routes, and the worse one is the documented fallback

`board_from_correspondences()` builds a `cv2.aruco.Board` whose object points are marker corners **expressed in the UNV frame**. The board pose returned by `estimate_pose()` therefore *is* the UNV→camera registration. `SpatialRegistration` computes the same transform independently via Kabsch — fed per-marker `tvec`s from individual `SOLVEPNP_IPPE_SQUARE` solves on single 12 mm markers.

Same pixels, same noise, 4 markers on an 80 mm plate at 0.5 m, 0.2 px corner noise:

```
(a) Kabsch on per-marker solvePnP centres   : RMS node error = 3.83 mm  (p95 6.49)
(b) single joint board solvePnP over corners: RMS node error = 0.39 mm  (p95 0.70)
                                               ratio = 9.7x worse
```

Route (a) discards the joint constraint by collapsing each marker to an independently-solved centre. `eyelab_gui.py:1573–1579` runs it every frame; `_draw_registered_wireframe()` then takes the board-pose branch and returns before ever using it. The code comment calls it "legacy centre registration."

So: the fallback path is ~10× less accurate than the path already running, it is dead in board mode, and because of S2 it would return `None` anyway on any flat specimen. Three reasons it has never been noticed.

`.docs/THEORY.md` §7.4 specifies a weighted Kabsch with weights ∝ 1/distance² — not implemented; the fit is unweighted with no outlier rejection, so one bad correspondence corrupts the whole transform.

### S6 — The calibration acceptance criterion is a fit statistic, and the theory doc already says so

`calibrate.py` accepts a calibration on `rms < 1.0 px` alone (warning above it). `.docs/THEORY.md` §3.3, *"How the residuals lie to you"*, lists exactly the three checks that are missing:

| THEORY §3.3 requires | Implemented in `calibrate.py` |
|---|---|
| Corner coverage across the frame | no |
| Tilt diversity, views at ±30° | no |
| Per-view RMSE, drop outlier frames | no |

`MIN_FRAMES = 15` counts frames, not viewpoint diversity — fifteen near-frontal captures give a degenerate fit that separates `fx` from `Z` poorly and typically yields a *lower* RMS than a well-conditioned calibration. `_detect_charuco` also accepts a view with as few as **4** corners.

Related, and worth taking together with S1b: `cv2.calibrateCameraExtended` returns per-view errors and **standard deviations of the intrinsics**. Those σ values are the principled input for both an honest quality report and a physically-scaled Kalman `measurementNoiseCov` (see §5, item 3).

### S7 — `_points_are_planar` uses an absolute tolerance on a count-dependent quantity

`LStructureDetector._points_are_planar(tol_m=1e-4)` thresholds the smallest singular value of the centred point matrix, which grows with both out-of-plane spread *and* point count.

```
out-of-plane scatter 0.05 mm -> 2 markers: planar     3: planar     4: NON-planar 6: NON-planar
out-of-plane scatter 0.10 mm -> 2 markers: NON-planar 3: NON-planar 4: NON-planar 6: NON-planar
```

Two consequences. The IPPE-vs-ITERATIVE solver branch flips with *marker count* at fixed physical flatness. And since hand-placed markers on a real flange will not be flat to 0.1 mm, the multi-marker planar branch effectively never fires — so the CHANGELOG's claim that *"Planar point sets (one marker, **or several coplanar markers**) are now solved with SOLVEPNP_IPPE"* holds only for the single-marker case. A relative test (`σ_min/σ_max`) fixes it.

### S8 — Error handling, coverage, and the shape of `eyelab_gui.py`

- **28 blind excepts.** CI's ruleset (`E9,F63,F7,F82`) passes cleanly, which is good discipline, but it hides 66 findings under `F,B,PERF,RUF,SIM,C4`. The blind excepts matter most in the pose path: `_solve_board_pose` swallows a `solvePnPRefineLM` failure and silently keeps the unrefined pose; `RoiRedetector._extract_board_geometry` returns `{}` on any exception, silently disabling ROI recovery for the whole session; `detect()` swallows `refineDetectedMarkers` failures. In a measurement pipeline these degrade into wrong numbers rather than errors.
- **`zip()` without `strict=`** (6 sites) — `zip(ids, obj_points)` in `_extract_board_geometry` truncates silently on a length mismatch.
- **Coverage 33 %.** `pose_lock` 86 %, `registration` 84 %, `overlay` 98 %, `unv_writer` 93 % are respectable. At 0 %: `eyelab_logger`, `generate_markers`, `gui_markers`, `gui_common`, `webcam_pipeline`. `eyelab_gui.py` is not imported by any test at all.
- **`eyelab_gui.py` is 1 854 lines and 94 defs/classes.** The 2026-07-08 modularization extracted `gui_calibration` / `gui_markers` / `gui_common` / `gui_geometry_editor` (1 821 lines combined) but the shell did not shrink proportionally. Against your stated preference for modularity, the AR loop (`_ar_loop`, `_draw_registered_wireframe`, `_draw_board_pose_wireframe`, `_ar_status_text`, `_update_detection_diagnostics`) is a coherent, testable unit that has no UI dependency beyond the canvas write and is the obvious next extraction — it is also the code the EyeLab Service (ADR-001 Step C) will need to reuse headlessly.
- **Duplicated LK logic.** `OpticalFlowTracker` (pose_estimator) and `MarkerCarryover` (pose_lock) implement overlapping Lucas-Kanade tracking with byte-identical `LK_PARAMS`, but only `MarkerCarryover` validates the tracked quad (bounds, area ratio, convexity). `OpticalFlowTracker.track()` has no such check, and both feed corners into the pose solve as if they were decoded detections.
- **`ThreadedCapture._reader`** busy-loops with no sleep and no handling of `ok == False` — a camera that fails mid-session spins a core at 100 % with no error surfaced.

## 5. Hypotheses tested and rejected

Recorded so they are not re-raised. All were plausible on reading and did not survive measurement.

1. **`kf.statePost[:6] = meas` is a no-op** (OpenCV property-copy semantics). It is not — the slice assignment writes through in cv2 4.14. Seeding works.
2. **The Kalman filter is ~100× too sluggish** because `measurementNoiseCov = I·1e-2` implies σ = 0.1 m. Only the `Q/R` ratio sets the gain: measured 90 % step rise time is 133 ms with ~13 % overshoot, and steady-state lag on a noise-free constant-velocity ramp is 0.0 mm. Responsive enough.
3. **The isotropic `R` across metres and radians is a defect.** Downgraded to a design remark: it prevents tuning translation and rotation smoothing independently, but it costs nothing measurable today. It becomes worth fixing only alongside S6, when real σ values exist to put in it.
4. **Rodrigues smoothing breaks near θ = π** (the near-face-on board pose). `align_rvec` handles it correctly — it collapses a raw 359.8° frame-to-frame jump to 0.2°, and peak smoothed angular error crossing θ = π is 0.00° versus 0.003° in a control sweep far from π. Well-designed code.
5. **`idx = 0 # solutions are sorted by reprojection error` is an unfounded assumption** about `solvePnPGeneric`. Verified over 400 two-solution cases: the first solution was the lower-error one in 100 % of them. Comment is correct.
6. **12 mm markers cost pose accuracy.** They do not — board-pose accuracy is set by the marker *layout extent*, not marker size: 12 mm and 50 mm markers on the same 80 mm layout give 0.21 mm vs 0.16 mm position RMS at 0.4 m. What 12 mm does limit is **decode range**: edge length falls to 13.3 px at 0.8 m, below the ~20 px reliability threshold. Frame it as a detection-range constraint, not an accuracy one.
7. **The redundant per-frame work is a performance problem.** Measured at 1280×720: re-creating the CLAHE object costs 0.03 ms, `gray.copy()` 0.03 ms, per-marker `solvePnP` 0.009 ms (0.06 ms for six markers), `SpatialRegistration.compute()` 0.069 ms. All negligible. The frame budget is dominated by `detectMarkers` — 3.26 / 6.25 / 12.08 ms for the strict / balanced / forgiving presets — plus 2.4 ms of CLAHE. The redundancy in S5 is a **clarity** problem, not a speed one; do not "optimize" it, delete it.

One performance note that *is* actionable: the `forgiving` preset costs ~4× `strict`. With the AR loop scheduled on the Tk main thread via `root.after` at a 33 ms default, detection and UI redraw serialise — worth knowing before the same presets are carried to a phone-hosted Unity build.

## 7. Applied on 2026-09-18 (post-audit)

Tier-1 scaling work is done and verified; everything else in §4 is still open.

**S1a — marker size.** Default 12 mm -> 20 mm (`generate_markers.MARKER_SIZE_MM`), grid spacing 16 -> 26 mm so the quiet zone stays positive. Marker size is now recorded **per structure** as `defaultMarkerSizeMm` in that structure's marker config: `registration.read_marker_config()` / `MarkerConfig` read it, `save_marker_config(..., default_marker_size_mm=)` writes it, and the GUI adopts it on config load and persists whatever the operator sets. Per-marker `markerSizeMm` overrides still win. Old config files without the field load unchanged.

**S1b — calibration resolution.** Added `calibrate.CalibrationData`, `read_calibration()` and `describe_resolution_mismatch()`. `ArucoPipeline.start()` and `webcam_pipeline.run_pipeline()` now compare the calibration's recorded `image_width`/`image_height` against what the camera actually delivers and refuse to run on a mismatch, with a message naming both resolutions and the implied scale factor. `load_calibration()` keeps its two-tuple signature, so existing callers are unaffected; calibrations predating the size fields are not falsely rejected.

**S1c — UNV units.** `_parse_units` now reads pyuff's real keys (`units_code`, `length`, `force`, `temp`) with the old spellings as fallback, and `UNVParser.parse()` applies the length factor so **node coordinates are always metres**. Unit code 9 (USER_DEFINED, which `geometry.unv` and `lastra.unv` actually declare) registered. A file with an unknown unit code and no usable factor is now refused rather than silently assumed to be SI.

**Third key mismatch, found while fixing S1c.** `_parse_nodes` read `coord_sys` / `disp_coord_sys` for Dataset 2411; pyuff emits `def_cs` / `disp_cs`. Every node's coordinate system had therefore always defaulted to 0, which silently disabled `_validate_cs_references` for all modern-format files. (The legacy Dataset 15 path already used a both-spellings fallback and was correct.) Both spellings now accepted, and geometry spanning multiple coordinate systems — or using a cylindrical/spherical one — is refused with an explanatory error instead of being read as Cartesian in one frame.

**Verification.** 85 tests pass (the single error remains the known `tkinter`-absent one); CI's exact ruleset passes; no unused imports introduced. `python/test_scale_contracts.py` adds 16 regression tests that pin each contract *and* the "wrong but reprojects perfectly" property that hid these bugs, so a regression fails loudly rather than silently. Real repo assets were diffed against the pre-change parser: `box.unv`, `geometry.unv` and `lastra.unv` parse to byte-identical geometry; only the reported unit *name* changed, from a defaulted "SI" to the truthful "USER_DEFINED".

**Pre-existing, not addressed:** `test_assets/xrealprobox.unv` fails to parse (`pyuff`: "Error when reading data-set(s)") and did so before these changes. Its dataset types read as `[15, 82, 82, 82, 164]`, so the header is intact and the fault is inside one of the blocks. Worth a look, separately.

**S5 — registration strategy.** Investigated further and written up as a proposed decision in `docs/adr/0002-registration-strategy.draft.md`. Summary: the Kabsch path is ~10x less accurate for the live pose *and* a weaker diagnostic than per-marker reprojection residuals — but it is the only one of the two that is blind to marker roll, which makes it the natural bootstrap for recovering roll automatically. Measured: Kabsch bootstrap -> recover roll -> board solve gives 0.44 mm against 9.85 mm for today's board path when markers are applied at arbitrary roll, with roll recovered to 0.59 deg and nothing for the operator to measure. Awaiting a decision.
