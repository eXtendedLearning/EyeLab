# EyeLab project audit - revised 9 October 2026

## Scope and conclusion

Initial code review performed on 7-8 October 2026. Source locations in F01-F14 refer to the checkout
at commit `60f6978c3bb9a53bb81db06b2281e24d982cc20c` (the changes that were
uncommitted at the start of the audit were committed before the final rerun).
This audit was updated in place on 9 October after reading all three ADRs,
the September native-runtime investigation and the downloaded PC beta source.
The XREAL assessment and development sequence below supersede the 8 October
sequence. Historical findings and measurements are retained; the correction
table at the end records their current disposition. This revision is not a new
full code audit or test-suite run.

The Python webcam pipeline is an implemented research prototype, not yet a
validated metrological system. Its calibration, board-PnP, recording and replay
components provide a usable foundation. The initial review reproduced geometry,
pose-acceptance and frame-freshness defects; these were subsequently corrected
as recorded below. Deferred findings still limit validation. The Unity system is
a scaffold and implementation plan, not an operational XREAL application.

User-confirmed constraints: XREAL One Pro + Eye; desktop and Surface Pro 7 only;
Beam Pro has not arrived and no compatible Android phone is available. The final
application shows **only the wireframe and measurement points over the directly
visible specimen**. The camera image is tracking input, not the final displayed
background; grayscale is acceptable. A video composite is an intermediate
diagnostic, not fulfilment of the AR requirement. The Surface's confirmed display
connection makes it the initial integration host.

The user specifies point spacing of at least 50 mm, with 1 mm accuracy as the
desired target; working range will be explored experimentally. Before claiming
that target, define whether it bounds per-axis error, 3D radial error, projected
display error or a percentile of repeated measurements. Report these separately
until the acceptance definition is agreed. Grid spacing is not an accuracy proof.

This revision changes documentation only. New observations establish package
contents, binary identity and desktop USB/NCM connectivity, not camera capture,
tracking or optical registration.
Priority P1 means address before trusting measurements or building the affected
integration; P2 means address before repeatable deployment or publication.

## Findings

### F01 - P1 - Dataset 2420 is silently discarded (reproduced)

**Evidence:** `python/unv_to_json.py:309` expects `cs_id`, `cs_type`, `origin` and
axis arrays. The installed pyuff reader actually emits `CS_sys_labels`,
`CS_types` and `CS_matrices`. At line 153, displacement-CS validation is skipped
when the parsed CS list is empty.

A real temporary UNV, written with pyuff, contained cylindrical definition CS 7
and undefined displacement CS 99. `UNVParser.parse()` accepted it, reported zero
coordinate systems, and exposed an angular coordinate of 90 as Cartesian `y=90.0`.
Thus the documented rejection of non-Cartesian geometry is not effective for
this input. This is distinct from the already-fixed Dataset 164 unit-key defect.

**Ideal solution:** adapt all supported datasets to the actual pyuff contract;
validate nonzero definition and displacement references even when Dataset 2420
is absent. Until transformations are implemented, reject unsupported coordinate
systems explicitly. Define the output frame and normalize CS translations as
well as node coordinates to metres if those transforms are exported.

**Acceptance:** pyuff write/read integration fixtures for rectangular, cylindrical,
spherical, missing and multiple CS definitions; no silent fallback to global or
Cartesian coordinates. Include representative Testlab exports, not just mocks.

### F02 - P1 - Marker count bypasses pose-quality gates (reproduced)

**Evidence:** `python/pose_lock.py:304-313` accepts any pose with at least
`trusted_min_markers` (default 3) before RMS and motion checks. This applies after
lock too. After ten good frames, a three-marker pose with 25 px reprojection RMS
and a 0.30 m translation jump was accepted as a measurement, not coasting.

**Ideal solution:** apply finite-value, positive-depth and reprojection checks to
every candidate. Separate initial acquisition, sustained tracking and explicit
reacquisition; make motion gates time-aware. Treat marker count as supporting
evidence, not permission to bypass checks. Apply planar-ambiguity handling based
on geometry, not only the number of markers.

**Acceptance:** reject injected high-RMS, NaN, negative-depth, ambiguous and
discontinuous poses at every supported marker count; reacquire a genuinely moved
specimen through a documented state transition.

### F03 - P1 - Cached images masquerade as fresh measurements (reproduced)

**Evidence:** `python/pose_estimator.py:275-277` returns a copy of the same cached
image on every call. There is no frame sequence or atomic capture timestamp.
One injected frame produced 100 successful reads without another camera read.
`process_frame()` timestamps processing (`:1288`), and validation timestamps
recording (`python/validation/capture.py:66`); its loop at line 150 counts each
processed result as another frame.

**Impact:** rapid consumers can inflate sample counts and apparent detection
rates, satisfy acquisition confirmation using one image, and update the Kalman
filter repeatedly from stale evidence. A blocked capture read can leave that
image available indefinitely; the five-second failure limit only advances when
the native read returns.

**Ideal solution:** an immutable frame packet containing source/session ID,
sequence, image, device capture timestamp when available, host receive timestamp,
clock domain and image mode. Process each sequence once; enforce an age deadline
independently of reader progress. Preserve frame identity through pose, recording
and presentation. Do not label host receive time as exposure time.

**Acceptance:** a frozen source cannot acquire/sustain a fresh lock; duplicate,
delayed and out-of-order frames are handled explicitly. Recorded sample count
equals unique accepted source sequences. Video overlays use the same image as
the pose solve.

### F04 - P1 - Current uncertainty verdicts exceed their evidence (source review)

**Evidence:** `python/validation/uncertainty.py:29-30` assumes 0.02 mm print
placement and 0.05 mm paper flatness without measured provenance.
`python/validation/fold.py:27,90-111` assumes a 0.1 degree intrinsics-bias floor
and reduces frame scatter by sqrt(n), although independence is not established.
The same intrinsics participate in fold fitting and subsequent validation.

The independent saddle detector is a useful improvement over locating ground
truth near EyeLab's predictions. It still does not establish independent absolute
3D accuracy. Uniform scale can cancel in ideal image reprojection; this does not
make the conversion of a nonzero pixel error into millimetres scale-independent.

**Ideal solution:** identify each uncertainty term's source, distribution,
correlations and sensitivity; distinguish measured values from assumptions.
Validate fold angle against an independent reference and perturb/recalibrate
intrinsics. Use independent sessions and effective sample counts or block-based
analysis for correlated frames. Keep image-plane alignment, metric pose accuracy,
repeatability and dynamic display registration as separate outcomes. Retain the
independent absolute-distance/step tests.

An instrument's stated +/- value is not automatically a rectangular bound, and
k=2 is not automatically exact 95% coverage. Make TUR>=4 an explicit project
decision, not a general proof of accuracy. The relevant basis is the
[JCGM uncertainty framework](https://www.bipm.org/en/web/guest/publications/guides),
particularly GUM sections 4.2, 4.3, 5.2 and 6.

**Acceptance:** no unconditional metrological PASS when essential budget terms
are unverified; demonstrate coverage and independent physical checks before
claiming a 1 mm capability. Synthetic tests alone cannot provide that evidence.

### F05 - P1 - The planned spatial transform/time contract is incomplete (design)

**Evidence:** `docs/tasks/T2.6-implementation-checklist.md:411-444` combines an
SDK frame timestamp with separately sampled Unity head poses without defining
their clock relationship. An image older than 200 ms is mapped to the oldest
history entry, rather than rejected. Head-camera extrinsics are identity in v0.
The composed model-to-world pose is misleadingly named `worldToStructure`.

**Ideal solution:** define transforms as `T_destination_from_source` and use:

```
T_world_from_structure(t_capture) =
    T_world_from_head(t_capture)
    * T_head_from_camera
    * T_camera_from_structure(t_capture)
```

Bind timestamps to the actual acquired image handle; map SDK and host clocks
explicitly. Interpolate bracketing head samples, reject uncovered/stale times,
and reset histories/anchors on session or tracking-origin changes. Specify raw
versus filtered camera pose; filter the stationary world anchor after composition
rather than silently treating a lagged camera-frame pose as instantaneous.

Apply basis conversion consistently to poses AND geometry. For
`F=diag(1,-1,1)`, `R'=F R F`, `t'=F t`, and scalar-first
`q'=(w,-x,y,-z)` when both local and camera coordinates change basis.

**Acceptance:** synthetic translation/rotation chains, basis round-trips,
capture/head timestamp skew, tracking loss/relocalization and latency-injection
tests. Measure p95 pose age and dynamic alignment, not only average service time.
Illustration, not a measurement: 20 ms uncompensated rotation at 60 degrees/s
produces about 10.5 mm lateral error at 0.5 m.

### F06 - P2 - Kabsch rejects valid planar layouts (reproduced)

**Evidence:** `python/registration.py:338-340,448-460` treats a small third
covariance eigenvalue as degeneracy. Three non-collinear points necessarily span
a plane. An exact 100 mm triangle, transformed rigidly without noise, returns
`None` from `compute()`.

**Ideal solution:** detect rank below two using a scale-relative singular-value
test on both point sets; preserve reflection correction and check residuals.
Keep board-level PnP as the primary image-pose estimator. This defect affects the
Kabsch registration path, not every planar board-PnP solve.

**Acceptance:** planar triangles and larger planar sets recover known transforms;
collinear/coincident sets reject; results remain consistent across object scales.

### F07 - P2 - Capture shutdown can release a device still being read (source)

**Evidence:** `python/pose_estimator.py:279-286` waits two seconds, records that
the reader is still alive, then calls `cap.release()` regardless. The source
comment itself identifies concurrent release/read as a known Windows hang risk.
This audit did not reproduce a native driver hang on hardware.

**Ideal solution:** keep device lifecycle under one owner. Where drivers cannot
be interrupted reliably, isolate capture in a child process with bounded IPC and
a controlled termination policy. A timeout must bound caller waiting, not merely
produce a diagnostic flag before another potentially blocking native call.

**Acceptance:** cancellation, unplug and simulated blocked-read tests leave the
UI responsive; repeated open/stop cycles do not leak readers or native handles.

### F08 - P2 - Bridge specification is internally incompatible (design)

**Evidence:** the T2.6 header at line 137 is called 16 bytes but its fields total
20: 4+1+3+4+8. CONTEXT uses `timestampNs`; the response example uses
`timestamp_ns`. Its geometry DTO at line 379 expects string `units`, while the
parser emits an object. The board example omits marker roll and still uses
12 mm defaults. Calibration paths predate the shared config tree.

**Ideal solution:** version one executable schema and golden fixtures before
writing both endpoints. For the listed binary fields, use an explicit 20-byte
layout such as Python `<4sB3xIQ`; define length limits, byte order, sequence wrap,
invalid/no-pose messages, source/clock identity and calibration/geometry hashes.
Preserve `IArucoPoseBridge`; keep WebSocket dependencies inside implementations.
Use the existing shared configuration service and a headless processing entry
point. Bound queues and isolate per-session detector/filter state.

**Acceptance:** Python/C# cross-language fixture tests; malformed, oversized,
duplicate, stale and reconnect messages fail predictably. Default to loopback;
remote operation requires explicit binding and authenticated access.

### F09 - P2 - Probe success and licence conclusions are too weak (reproduced/source)

**Evidence:** `python/xreal_headpose.py:267-280` requires only one nonidentity
sample for delivered data. A constructed report with resolved requirements,
initializing tracking, zero clock and one nonidentity sample reports `ok=True`.
At line 322, refusal of two feature families is described as an empty licence
list. It proves neither the absence of other licensed features nor the absence
of a licence.

**Ideal solution:** separate library initialization, device connection, valid
stream delivery and usable tracking. Require finite rigid poses, valid tracking
state, increasing device timestamps, sufficient duration and a motion response
plus an unplugged negative control. Say exactly which calls were refused.

**Acceptance:** identity-only, NaN, stale, initializing and disconnected streams
cannot pass the tracking gate. Treat the recorded September failures as
pre-firmware-update results until rerun, not current hardware measurements.

### F10 - P2 - Calibration profiles lack a complete compatibility contract (source)

**Evidence:** `python/calibrate.py:346-406` stores image size and board dimensions,
but not stable device identity, sensor/crop mode, focus or processing orientation.
At lines 419-432, missing legacy dimensions return the same result as a match.
`python/gui_calibration.py:447-473` checks corner/frame counts, not view diversity.

**Ideal solution:** bind profiles to source identity, mode, dimensions, crop,
rotation/mirroring and focus state; validate finite intrinsics/distortion. Treat
unknown legacy provenance as unverified for measurements. Add coverage/view
diversity checks and held-out views, keeping a compatibility override only for
clearly labelled diagnostic use.

**Acceptance:** the wrong same-resolution camera or crop is rejected; focus/mode
changes invalidate the profile; repeated near-identical calibration views cannot
silently meet a quantitative quality gate.

### F11 - P2 - Two tests fail on the actual Windows development host (reproduced)

**Evidence:** 343 tests, 340 passed, 2 errors, 1 skipped on 8 October:

- `test_ar_watchdog.py:27`: `tearDown()` deletes the temporary directory before
  `addCleanup(wd.stop)` runs. Windows refuses deletion of the open JSONL file.
- `test_gui_calibration.py:62`: the test accesses `window.cap.release` after
  production cleanup correctly sets `window.cap=None`.

**Ideal solution:** register temporary-directory cleanup before watchdog cleanup
so LIFO ordering closes handles first; retain the mock capture reference before
calling `_finish()`. These failures are test-lifecycle defects, not evidence that
the calibration algorithm or watchdog logic necessarily fails. Add a Windows CI
job beside Linux; retain the deliberate narrow Ruff rules.

**Acceptance:** full suite passes on Windows and Linux; retain the intentional
skip only with its reason. Validate a fresh environment as well as the existing
venv. The current run is not a clean-install or Python 3.9 compatibility test.

### F12 - P2 - Recorded provenance cannot reconstruct a dirty experiment (source)

**Evidence:** `python/validation/capture.py:92-116` records commit plus dirty flag
and target/calibration hashes. It ignores untracked files for that flag and does
not archive the source revision/diff, target contents or dependency versions.
Two different dirty implementations can therefore have the same recorded ID.

**Ideal solution:** copy effective configs/targets, record dependency versions and
device/firmware/mode, and hash the executed source set including relevant untracked
modules. Store a reproducible source snapshot or require a clean tagged experiment
revision. Keep raw data immutable; give analyses their own version and parameters.

**Acceptance:** replay can identify and reconstruct the exact processing code and
configuration without relying on the current working directory's mutable files.

### F13 - P2 - Video and optical see-through gates are conflated (design)

**Evidence:** proposed ADR-003 puts IMU before camera and assumes an exposed
factory extrinsic supplies the required eye-camera relation. T2.6 Phase 8 calls
a four-alignment rigid head-camera fit SPAAM and accepts visual agreement near
one working distance. Neither establishes per-user, per-eye display projection.

**Ideal solution:** separate these products. Video overlay projects onto the
captured image and displays that image; it does not require world tracking for
correct image registration. Optical see-through requires the full camera/head/
eye/display model, tracking and presentation-time compensation. Factory
camera-to-head calibration does not by itself determine the wearer's eye position
or guarantee correct display projection. This distinction is consistent with
[HMD calibration research](https://pmc.ncbi.nlm.nih.gov/articles/PMC3142613/).

**Acceptance:** independent gates for video alignment and optical alignment;
optical checks at held-out positions/depths, each eye, motion and repeated fitting.
Do not describe a fullscreen video panel as a world-registered optical overlay.

### F14 - P2 - Documentation mixes observations, assumptions and obsolete status

**Evidence:** CONTEXT and docs/README retain May status snapshots beside newer
updates. The September audit's string-search verifier still treats compatibility
key names as evidence of unfixed bugs. The Nebula audit's early safety/capability
assertions are stronger than export inspection supports. Current CONTEXT's NCM
range estimate treats canonical ArUco resampling size as a detector pixel limit
and compares image widths without establishing equal field of view.

**Ideal solution:** a dated capability matrix with columns for host, firmware,
transport, camera mode, tracking, display and evidence; explicit labels for
observed/documented/hypothesized. Replace source-string checks with behavioural
tests. Mark historical material clearly. Determine working range from calibrated
focal length, exposure, contrast and empirical detection/accuracy sweeps. A static
binary audit cannot certify absence of malicious behaviour or zero firmware risk.

**Acceptance:** one current status entry per capability; no instruction to rerun
a firmware probe that only resolves, but never calls, the relevant firmware API;
no performance or safety claim without its scope and evidence.

## XREAL reassessment - 9 October 2026

### Objective and consistency with every ADR

The deliverable remains a wearer-aligned optical wireframe and measurement
points over the physical EMA specimen. Eye images support ArUco registration;
showing those images in the glasses is only a diagnostic. Successful camera
capture alone does not demonstrate optical alignment or the desired 1 mm target.

| Decision | Recorded status and implication for this investigation |
|---|---|
| [ADR-001: OpenCV bridging staircase](adr/0001-opencv-bridging-staircase.md) | Accepted. Start with Python processing behind `IArucoPoseBridge`; transport belongs in its implementation. The documented deployment is Android Unity plus a PC/Surface service. A Windows Unity client with a local service is a candidate host adaptation of that boundary, not an implemented or accepted replacement deployment. Its old 10 mm pivot threshold does not satisfy the later 1 mm user target. |
| [ADR-002: registration strategy](adr/0002-registration-strategy.draft.md) | Proposed. Joint board-corner PnP and Kabsch/bootstrap intentions are independent of the rendering host. Do not describe proposed board-learning work as implemented or equate synthetic residuals with physical accuracy. |
| [ADR-003: Eye POV and rigid coupling](adr/0003-eye-pov-rigid-coupling.draft.md) | Proposed. The Eye is rigid to the glasses and supplies the desired wearer camera viewpoint. Surface-camera registration would additionally need the time-varying Surface-to-head transform; orientation alone is insufficient. Camera-to-head extrinsics, timestamps and per-eye projection remain necessary for optical rendering. |

The Surface is the integration host because its DP display path already passed
S1. The desktop can support source inspection and possibly data-only tests; its
current connection cannot validate the glasses display. Neither host has yet
demonstrated the complete EyeLab XR loop. Beam Pro remains an alternative future
Android host, not a reason to discard the existing Python implementation.

### What `Standalone/RGBCamera/RGBCamera.unity` is

Unity is the engine and authoring environment. A `.unity` file is a scene asset:
objects, components and references loaded by a Unity project. Here it is a vendor
camera demonstration wired to `RGBCameraExample.cs`, with start/stop capture and
YUV image display. `Standalone` identifies its desktop sample family; it does
not mean the scene file is independently executable.

Opening the scene and entering Play tests it inside the Editor. Building a
Windows application is a separate step that packages the scene, scripts, engine
runtime and plugins into an executable and supporting files. The resulting
application can run on the Surface without the Unity Editor. It runs on the
Surface CPU/GPU and communicates with the glasses; it does not turn the Surface
into Android or install Unity on the glasses. See Unity's
[scene documentation](https://docs.unity3d.com/6000.0/Documentation/Manual/CreatingScenes.html)
and [Windows build documentation](https://docs.unity3d.com/6000.0/Documentation/Manual/WindowsStandaloneBinaries.html).

Therefore this procedure could lead to a Windows EyeLab client, conditional on
runtime tests. Running or building the sample alone produces a camera demo,
not EyeLab: no UNV registration, Python bridge or calibrated optical wireframe
is supplied by that scene.

### Conditional Surface implementation

```text
Eye camera -> Windows Unity client -> IArucoPoseBridge -> local Python service
                                                     ArUco / board PnP / UNV
                   <- pose + frame identity/timing <-
capture-time head pose + camera/head calibration -> structure anchor
presentation-time head pose + per-eye projection -> wireframe -> Surface DP
```

This retains the accepted processing boundary. A loopback connection removes
the wireless hop; image acquisition, serialization, processing and rendering
delays still need measurement. Capture-time device timestamps must be related
to head-pose time; host receipt time is not exposure time. A restricted
marker-visible mode may use visual pose without persistent world tracking,
but motion compensation and persistence must be demonstrated separately.

Missing implementation verified in the current checkout: the Unity EyeLab
folders contain placeholders, the only project scene is `SampleScene.unity`,
and no EyeLab C# bridge or Python WebSocket service is present. The modules for
geometry and image processing exist; wrapping them as a headless service,
implementing the client, calibration and optical rendering is still work.
No Surface performance or final spatial accuracy follows from sample success.

## XREAL development sequence (revised 9 October)

### A. Camera/pose diagnostic prototype on Surface Pro 7

1. Retain the corrected F01-F03/FramePacket baseline and outstanding findings
   recorded below. Do not repeat already-completed fixes as prerequisites.
2. Run the isolated Windows beta RGB sample using the
   [bounded procedure](XREAL-PC-BETA-2026-10-09.md#next-experiment-isolated-unity-camera-sample).
   Jack performs Editor/Play/build actions. Keep the main Android project on
   3.1.0. Record current firmware without updating, actual live frames,
   resolution, advancing timestamps, rate and restart behaviour. A desktop
   failure without DP must be distinguished from a Surface failure. A Windows
   player build on Surface is a separate deployment gate after Editor capture.
3. If the sample fails, capture the failure stage and log before choosing a
   fallback or contacting XREAL. Existing desktop USB/NCM/TCP observations do
   not establish a video stream. The community
   [NCM implementation](https://github.com/Aloim/Grayscale-Feed-Xreal-One-Pro-Eye-Windows-Nebula-Beta-needed-)
   describes a beta-firmware-dependent grayscale route; it is a candidate,
   not proof that this unit currently works. Read the protocol implementation
   and identify the actual sensor, frame boundary and mode before integration.
4. If the beta and NCM routes are unavailable, inspect the camera route in
   [xr-tools](https://github.com/0xcaff/xr-tools). Any USB-mode change needs a
   separate, explicit, reversible procedure. Time-box feasibility work; do not
   substitute webcam success for Eye-camera success.
5. Calibrate the exact delivered Eye image mode. Feed it through the existing
   board-PnP/overlay code and inspect a same-frame composite on the Surface monitor
   (optionally in the glasses as a diagnostic panel, explicitly not registered AR).
   Keep acquisition, processing, display and recording
   independently testable. Local processing is the first baseline; desktop
   offload is conditional on measured Surface performance.
6. Validate stationary alignment, movement, unplug/reconnect, source freezing,
   latency and a sustained session. Sweep working distance/angle for >=50 mm point
   spacing; evaluate the 1 mm target without assuming it is achievable. Initial use
   is a supervised bench experiment, not
   unvalidated impact guidance.

This does not require buying a desktop display adapter or waiting for Beam Pro.
It does require proving a usable Eye-camera source. Until that gate passes, the
end-to-end glasses-camera prototype remains unverified.

### B. Optical see-through registration

After A: demonstrate usable tracking and its clock, obtain/validate camera-head
extrinsics, define per-eye projection, implement the corrected capture-time anchor
composition and presentation-time rendering, then validate static and dynamic
spatial error. Render only the wireframe, labels and points over the real specimen.
The camera must recover translation as well as orientation. Camera-only marker
tracking may support a restricted marker-visible mode; persistence during marker
loss and motion compensation require separately demonstrated tracking capability.
Do not make raw IMU access a universal prerequisite if a valid fused pose/rendering
path supplies the needed information. Preserve `IStructureAnchor` and
`EwmaStructureAnchor` contracts.
For a Windows client, first verify changing translation/rotation, tracking state,
usable clocks and concurrent camera/tracking through the vendor lifecycle.
Then implement the local Python bridge and calibrated rendering. An Android
host, when available, permits the original deployment through the same
`IArucoPoseBridge` boundary. The official
[RGB camera guide](https://docs.xreal.com/Camera/Access%20RGB%20Camera) and the
locally inspected Standalone sample establish API/source availability, not
successful operation on these hosts. Support/licensing and firmware
compatibility remain unresolved. Preserve the main pinned SDK during the test.

### C. Hammer events and Testlab integration

Keep spatial guidance, impact-time localization, accepted EMA acquisition and
Testlab write-back as separate milestones. First validate a read-only Testlab
adapter against the installed version/type library. Do not implement guessed
COM members or equate a nearby hammer with a valid measured FRF. Use calibrated
tip geometry, synchronized force/acquisition events, event IDs and an explicit
abstention state. Relevant prior work uses impact-triggered imaging and calibrated
marker assemblies: [Cepon et al., Experimental Techniques](https://link.springer.com/article/10.1007/s40799-023-00646-0).
